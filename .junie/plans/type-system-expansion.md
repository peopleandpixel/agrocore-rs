## Key Design Decisions

- **Variety/breed names are NOT translated** — they are proper names (Chardonnay, Merlot, Tempranillo, Holstein, Merino) that remain the same across languages
- **Attribute labels need translation**: berry_colour → "Beerenfarbe"/"Couleur de baie", use_kind → "Verwendung"/"Usage", origin → "Herkunft"/"Origine", etc.
- **Migration 0036** will be a direct copy of `catalogue_seed.sql` — it's already idempotent via ON CONFLICT DO UPDATE
- **Species common_name** in crop_species is already in English; translation can happen via i18n keys like `species_vitis_vinifera: Weinrebe` if needed, but scientific names are universal
- **Category labels** already exist in i18n (variety_category_weinrebe_variety, etc.) — no change needed

## Reference-Daten (Rassen, Rebsorten, Oliven) — Architektur

### Frage: Wo sind die Rassen, Rebsorten und deren Zusatzinfos?

**Antwort: Sie bleiben in den dedizierten Tabellen `varieties` und `breeds`, NICHT in `type_entries`.**

### Warum nicht in type_entries?

`type_entries` ist für **einfache enum-ähnliche Typen** gedacht (Code + Name + Übersetzungen + Hierarchie). Die Referenzdaten sind **reiche Entitäten** mit vielen Attributen:

| Datenquelle | Einträge | Zusatzattribute |
|---|---|---|
| `eu_grapes_annex1a.json` | 882 Rebsorten | `vivc_no`, `berry_colour`, `sex`, `countries` (Array), `uses`, `synonyms`, `national_id`, `years` |
| `olive_cultivars.json` | 87 Olivensorten | `synonyms`, `origin` |
| `breeds_wikipedia.json` | 79 Rassen | `birth_weight_kg`, `mature_weight_kg`, `female_weight_kg`, `eggs_per_year`, `wool_kg_per_year`, `wool_micron_min/max`, `gestation_days`, `litter_size`, `use`, `origin`, `height_m` |

Diese Attribute passen nicht in `type_entries` (die hat nur `name`, `code`, `parent_id`, `metadata` JSONB).

### Aktuelle Architektur

```
graph LR
    TD[type_entries : variety_category] -->|category_id FK| V[varieties table]
    CS[crop_species] -->|global_species_key FK| V
    V -->|extra columns| E[vivc_no, berry_colour, registration_countries, synonym_names, use_kind]
    
    TD2[type_entries : species] -->|species_id FK| B[breeds table]
    CS2[crop_species] -->|global_species_key FK| B
    B -->|extra columns| F[weights, eggs, wool, gestation, origin, use_kind]
```

**Konkret:**

1. **`varieties` Tabelle** – Enthält:
   - `name`, `category` (aus `variety_category` type_entries via `category_id: Uuid`)
   - `global_species_key` → `crop_species` (z.B. `vitis_vinifera`, `olea_europaea`)
   - **Grape-spezifisch:** `vivc_no`, `berry_colour`, `registration_countries` (TEXT[]), `use_kind`, `synonym_names` (TEXT[])
   - **Olive-spezifisch:** `synonym_names`, `origin` (in metadata oder extra Spalte)

2. **`breeds` Tabelle** – Enthält:
   - `name`, `species` (legacy text), `global_species_key` → `crop_species`
   - **Performance:** `birth_weight_kg`, `mature_weight_kg`, `female_weight_kg`, `eggs_per_year`, `egg_production_strain`, `wool_kg_per_year`, `wool_micron_min/max`, `gestation_days`, `litter_size`, `milk_kg_per_year`
   - **Meta:** `origin`, `use_kind`, `source`, `source_ref`

3. **`crop_species` Tabelle** – Enthält:
   - `species_key` (z.B. `vitis_vinifera`, `olea_europaea`, `bos_taurus`)
   - `scientific_name`, `common_name`, `kingdom` (plant/animal)
   - Wird von BOTH `varieties` und `breeds` referenziert

4. **`type_entries`** – Enthält NUR:
   - `variety_category`: grape, olive, wheat, apple, etc. (Kategorien zur Gruppierung)
   - `species`: cattle, sheep, goat, etc. (Tierarten als Typ-Referenz)
   - Dient als **Klassifikation**, nicht als Detail-Datenbank

### Datenfluss bei build_catalogue_seed.py

Der Generator (`scripts/build_catalogue_seed.py`):
1. Liest `eu_grapes_annex1a.json` → INSERT INTO `varieties` (mit vivc_no, berry_colour, registration_countries, etc.)
2. Liest `olive_cultivars.json` → INSERT INTO `varieties` (mit synonym_names)
3. Liest `breeds_wikipedia.json` → INSERT INTO `breeds` (mit allen Performance-Daten)
4. INSERT INTO `crop_species` für die Species-Referenzen
5. Alles idempotent via `ON CONFLICT DO UPDATE`

### Verbindung zwischen type_entries und Reference-Daten

- `varieties.category_id: Uuid` → `type_entries` (variety_category) – bestimmt die Kategorie (Weinrebe, Olive, etc.)
- `breeds` hat KEINE type_entries-Referenz – nutzt stattdessen `crop_species.species_key` direkt
- Die `variety_category` in type_entries dient nur als **Filter/Gruppierung** in der UI
- Die eigentlichen Sorten/Rassen mit allen Attributen bleiben in `varieties`/`breeds`

### Zusammenfassung

| Komponente | Zweck | Beispiel |
|---|---|---|
| **type_entries** | Einfache Typen, Enum-Ersatz | crop_type: wheat, site_type: vineyard, equipment_type: tractor |
| **crop_species** | Wissenschaftliche Arten | vitis_vinifera, olea_europaea, bos_taurus |
| **varieties** | Reiche Sorten mit Attributen | Chardonnay (vivc_no: 2674, berry_colour: white, countries: [DE, FR, IT...]) |
| **breeds** | Reiche Rassen mit Performance | Holstein (mature_weight_kg: 650, milk_kg_per_year: 9000) |

### Wichtige Design-Entscheidungen

1. **Caching-Strategie**: Typen werden beim ersten Laden gecacht (in einem `WriteSignal` im App-Context). Bei Änderungen an Typen wird der Cache invalidiert.
2. **Fallback**: Falls die API nicht erreichbar ist, zeigt der Dropdown die letzten gecachten Werte.
3. **UUID-Handling**: Der Dropdown gibt die UUID des ausgewählten Typs zurück, nicht den Code.
4. **Backend-Kompatibilität**: Die Create/Update Requests senden jetzt `*_id: Uuid` statt `*_type: String`.
5. **SuperAdmin vs Admin**: SuperAdmin kann systemweite Typen bearbeiten, Admin nur tenant-spezifische.
